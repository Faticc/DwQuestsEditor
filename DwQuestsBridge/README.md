# DwQuestsBridge — клиентский мод для редактора квестов

Мод к Minecraft 1.7.10 (Forge), который делает две вещи:

1. **Выгружает ассеты из живого клиента** — иконки всех предметов пака (включая
   варианты, отличающиеся только NBT), текстуры модов DwQuests/DwCore и шрифт.
   На выходе — дерево ровно той формы, что читает редактор.
2. **Связывает игру с редактором** — локальный HTTP-мост: редактор берёт вкладки
   прямо из памяти клиента, просит дорисовать недостающую иконку и отдаёт
   изменённую вкладку обратно в игру.

Мод целиком клиентский: серверу о нём знать не нужно, `acceptableRemoteVersions = "*"`.

## Сборка и установка

```bat
build.bat
install.bat "C:\Users\User\McSkill\clients\Industrial_1.7.10"
```

Воркспейс — GTNH-convention (RetroFuturaGradle), как остальные моды пака.
Jar-ы для компиляции берутся из клиента; путь задаётся свойством `clientDir`
в `gradle.properties` (или ключом `-PclientDir=...`).

Компилируемся против боевых jar-ов `DwQuests-1.2-client-final.jar` и
`DwCore-1.2-client-final.jar`: они не обфусцированы (проверено `javap`), так что
имена методов в рантайме те же. NEI — необязательная зависимость, обращение к
ней изолировано в `NeiStacks` и включается только если мод загружен.

## Команды в игре

Все команды клиентские: сервер о них не знает, прав не спрашивает.

| Команда | Что делает |
|---|---|
| `/dwqb icons [all\|quests\|registry] [--force]` | иконки предметов в `dwq_export/icons` |
| `/dwqb assets` | текстуры модов и шрифт в `dwq_export/game` |
| `/dwqb tabs [auto\|raw\|local]` | вкладки квестов в `dwq_export/tabs` |
| `/dwqb all` | ресурсы и иконки разом |
| `/dwqb icon <mod:name[:meta][{nbt}]>` | дорисовать одну иконку |
| `/dwqb paste <вкладка> [файл]` | залить вкладку в игру |
| `/dwqb bridge [start\|stop]` | мост с редактором |
| `/dwqb stop` / `/dwqb status` | прервать выгрузку / что сейчас происходит |

Выгрузка идёт **по кусочкам в тике клиента** (25 мс на тик по умолчанию): пак —
это больше десяти тысяч картинок, и одним куском игра бы зависла, а сервер успел
бы выкинуть по таймауту. Ход виден в чате и в логе.

## Что где оказывается

```
<клиент>/dwq_export/
  icons/img/<мод>/<имя>[_мета][~хеш].png     иконки 64x64
  icons/json/items.json                      имена, числовые id, ссылки на картинки
  game/assets/<домен>/…                      текстуры модов и шрифт
  tabs/<вкладка>.json                        вкладки квестов
  bridge.json                                порт и ключ моста
```

`icons` и `game` — это ровно то, что редактор ждёт увидеть в своём `runtime/`:
папку можно указать в его настройках как есть.

### Иконки вариантов с NBT

Старый `icon_exporter` ключевал картинки по `mod:name:meta`, поэтому все цветы
Botany (`Botany:itemFlower`, вид которых задан геномом в NBT) сливались в одну
картинку. Здесь ключ — ещё и NBT: хвост `~хеш` в имени файла, где хеш считается
от **приведённого** вида NBT (ключи отсортированы, суффиксы чисел убраны). Тот же
хеш независимо считает редактор (`NbtLite.canonical` + `ItemRegistry.hash8`), и
сходимость проверяется в его `SelfTest`.

Всех сочетаний генома всё равно не выгрузить — их слишком много. Поэтому главный
путь для таких предметов другой: редактор просит игру нарисовать **тот самый**
стек, который стоит в квесте (`GET /icon?stack=…`), и кладёт ответ к остальным
иконкам.

## Мост

Слушается только `127.0.0.1`, каждый запрос требует ключ (`X-Dwq-Token`) из
`config/dwqbridge.cfg`; порт и ключ дублируются в `dwq_export/bridge.json`, чтобы
редактору не нужно было ничего вводить руками.

| Запрос | Ответ |
|---|---|
| `GET /ping` | есть ли игрок в мире, сколько вкладок и квестов |
| `GET /tabs` | список вкладок |
| `GET /tab?id=X` | вкладка в формате редактора |
| `GET /icon?stack=X` | PNG иконки (с учётом NBT) |
| `GET /item?stack=X` | имя, числовой id, путь картинки |
| `GET /items` | весь реестр предметов одним ответом |
| `POST /export?what=icons\|assets\|tabs` | запустить выгрузку в игре |
| `GET /status`, `POST /stop` | ход выгрузки, прервать |
| `POST /paste?id=X` | отдать вкладку в игру |

Запросы ничего не трогают сами: всё, что смотрит в игру или рисует, уходит
заданием в главный поток (`ClientTicker`) — OpenGL и карта квестов принадлежат ему.

## Заливка вкладки обратно

Идёт штатным путём мода: JSON кладётся в буфер обмена, затем от имени игрока
выполняется `/dwq tab paste <вкладка>`. Команда `/dwq` требует второго уровня
прав, и эта проверка остаётся на сервере — мод только избавляет от ручного
копирования файла в буфер. Если прав нет, сервер просто откажет.

## Чего не хватает в выгрузке вкладок из памяти

Клиенту присылают не файл вкладки, а разобранные объекты (`CSPQuestSync`), и
часть полей в пакет не попадает:

* `broadcast` — не передаётся вовсе;
* строки наград восстановлены из `ItemStack` и списка команд: NBT и количество
  на месте, но исходный порядок «предмет-команда-предмет» не восстановить;
* `iconItem` с незнакомым id на клиенте уже стал бедроком.

Точную копию файла отдаёт `/dwqb tabs raw` — он просит у сервера `/dwq tab copy`
и забирает результат из буфера обмена. Нужны права на `/dwq`; в режиме `auto`
мод пробует точную копию и, если сервер не ответил, пишет сборку из памяти.


## Впрыск в запущенный клиент

Обычный мод в работающую игру не добавить: FML ищет моды, строит их и рассылает
этапы загрузки один раз при старте, а реестры к входу в мир уже закрыты. Но этот
мод в игре ничего не регистрирует — только клиентскую команду, обработчик тика и
свой поток с HTTP, — и всё это принимается в любой момент. Поэтому для него
впрыск работает:

```bat
attach.bat
attach.bat "C:\Users\User\McSkill\clients\Industrial_1.7.10"
```

Внутри — `attach/dwq-attach.jar`: подключается к чужой JVM через Attach API,
грузит себя туда агентом, находит загрузчик классов, которым загружен
`net.minecraft.client.Minecraft`, добавляет в него jar мода и зовёт
`DwqBridge.attach()`. Регистрация уходит в очередь главного потока
(`Minecraft.func_152344_a`): список команд и шину событий из чужого потока
трогать нельзя.

Важно именно **тот** загрузчик: в бою классы игры обфусцированы, мод собран под
SRG-имена, и совмещает их преобразователь FML внутри LaunchClassLoader. На
системном пути классов мод загрузился бы без преобразования и упал на первом же
обращении к игре.

Чего впрыск не даёт: мода нет в списке FML (`Loader.isModLoaded("dwqbridge")` —
false) и не будет при следующем запуске. Для постоянной работы — `install.bat`.

Если JVM откажется грузить агент на ходу (новые JDK умеют это запрещать),
клиенту нужен ключ `-XX:+EnableDynamicAgentLoading` — это разовый перезапуск,
дальше впрыск работает всегда. Подключаться должен JDK, а не JRE:
`com.sun.tools.attach` живёт в модуле `jdk.attach`.

**Когда впрыск невозможен в принципе.** Лаунчеры нередко запускают игру с
`-XX:+DisableAttachMechanism` — тогда в этой JVM механизм подключения выключен
целиком, и снять это может только тот, кто формирует строку запуска. Так делает,
например, лаунчер GribLand (там же `-XX:+PerfDisableSharedMem`, из-за которого
процесс не виден и в списке JVM — подключаться пришлось бы по `--pid`). Ломать
эту защиту незачем и не нужно: есть `install.bat` и перезапуск.

Агент собран под Java 8 (`DwqAgent`, класс-файл 52) отдельно от запускающей
половины (`Attacher`, 17): клиенты 1.7.10 бывают и на «восьмёрке», а она просто
не загрузит класс новее. Сам мод тоже Java 8 — проверено `javap`.
